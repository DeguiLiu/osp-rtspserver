## 0. 结论先行

1. **架构方向成立**：单 Reactor、固定槽位、共享 AU、每客户端独立 RTP 状态，符合资源受限直播服务的目标；生产路径基本无堆、无异常。
2. **代码质量好于“原型”**：parser/SDP/packetizer/RTCP/ingress/HSM/transport 分层清楚，单测和 E2E 已覆盖主要路径；干净构建下 `ctest` 10/10 通过，真实 H.264 ffmpeg 解码通过。
3. **P0 已基本闭环，但仍不能按“已达标”评价**：全局桶、UDP 端口对、interleaved channel、RTCP SR/RR、`input_seq` 已修；剩余主要是 TCP `tx_` 复制、8 槽与 500 ms 口径、SPS profile 校验，以及 16 路/ARM 证据不足。
4. **PHZ76/RtspServer 应“充分挖掘行为与用例”，不应“充分复制框架与实现”**：它的协议流程、SDP/Transport/RTP/RTCP 细节和边界场景值得作为一致性语料；它的每连接复制、动态缓冲、线程模型和静默 epoll 错误不值得照搬。
5. **C++17 应“用在零成本约束上”，不应“为语法而语法”**：当前代码已经用对了主要特性；真正的性能收益来自去掉 FU-A/TCP payload 复制、修正限流与调度，而不是增加模板或 `std::variant`。

## 2. 当前方案评价

### 2.1 成立的部分

- **单 Reactor 边界正确**：socket/RTSP/session/RTP 状态归 loop；编码器只做 `Acquire/Commit/Abort`，通过 SPSC + `Wake()` 桥接。
- **固定容量与 HSM**：server/session 生命周期用静态转移表；连接槽、帧槽、队列都是编译期常量。
- **fd 生命周期**：`DeferredCloseBatch` 延迟关闭，避免同一批 poll 结果把旧事件投给新连接；手动 TEARDOWN 后重连验证通过。
- **无堆生产路径**：`src/` 未使用 `std::string/vector/map/shared_ptr/function`；热路径以固定数组和视图为主。
- **测试基础**：parser、SDP、H.264/H.265 packetizer、RTCP、ingress、HSM、transport 都有独立单测；E2E 覆盖 TCP/UDP、RTP-Info、FU-A 重组、8 路并发、连接上限、慢客户端。

### 2.2 仍停留在“能跑”而非“可交付”的部分

- 互操作边界（UDP 端口对、interleaved channel）没有按真实客户端行为验证。
- 16 路容量只做了数学估算和 4 路冒烟，没有满负荷证据。
- RTCP、丢帧恢复、SPS/PPS 变化等设计承诺未闭环。
- 测试基础设施会把环境问题误判为 server 问题，导致结论不稳定。

## 3. P0 问题（验收前必须修）

### P0-1 全局 12 Mbps 令牌桶压死 16 路（已闭环）

**现象**：`global_bucket_` 以 12 Mbps 聚合限流，`Admit()` 先扣每客户端 8 Mbps 桶，再扣全局桶；全局拒绝时当前 AU 被丢弃并进入 `AwaitIDR`。

**证据**：`config.hpp` `kEgressRateBps`；`rtsp_session.cpp` 的 `kClientRateBps`/`kClientBurstBytes` 与 `RtspSession::Admit`。16 路 4 Mbps 即 64 Mbps，12 Mbps 只能容纳约 3 路平均值。

**影响**：16 路验收必然失败；全局拥塞还会让所有客户端反复等 IDR，表现为周期性卡顿/花屏。

**建议**：

1. 删除全局桶，保留设计中的每客户端 8 Mbps/32 KiB；
2. 若必须保留总出口保护，阈值至少设为 `kMaxConnections × 8 Mbps = 128 Mbps`，且只作为异常保护；
3. `Admit` 先检查两个桶的可用量，再一起扣减；不允许“客户端已扣、全局失败”；
4. 全局拒绝不应触发 `DropToAwaitIdr`，应优先对单客户端降级或等待。

**验收**：16 路 4 Mbps、30 min，`token_drops=0`；全局桶若存在，`available` 不成为瓶颈；单客户端 8 Mbps 峰值可跑满。

### P0-2 UDP `server_port` 不是 RTP/RTCP 端口对（已闭环）

**现象**：`UdpRtpTransport::Open()` 独立 bind 两个临时端口，响应里的 `server_port` 可能是 `36460-39004`，RTP 端口也不保证偶数。

**证据**：`rtp_transport.cpp` 的 `UdpRtpTransport::Open`；手动 SETUP 实测 `Transport: RTP/AVP;unicast;client_port=5000-5001;server_port=36460-39004`。

**影响**：不符合 RFC 3550 的 RTP/RTCP 端口约定；部分客户端、NAT、防火墙会拒绝或无法关联 RTCP。

**建议**：

1. 先为 RTP 绑定偶数临时端口，再为 RTCP 绑定 `RTP+1`；
2. 若 `RTP+1` 被占用，关闭并重试，最多 N 次；
3. 失败时回滚并返回 503/453，不能返回非连续端口对；
4. 把“`server_port` 连续且 RTP 偶数”加入 SETUP 单测和 E2E 断言。

**验收**：100 次 SETUP，`server_port` 全部满足 `rtcp == rtp+1` 且 `rtp` 为偶数；VLC/ffplay UDP 播放通过。

### P0-3 interleaved channel >1 协商成功后无媒体（已闭环）

**现象**：`ParseTransport` 接受 `interleaved=2-3` 并返回 200；`WriteInterleaved` 只允许 channel ≤1，导致媒体路径 `kFatal`，客户端无数据。

**证据**：`rtsp_session.cpp` 的 `ParseTransport`（接受 `kMaxInterleavedChannel=127`）、`rtp_transport.cpp` 的 `WriteInterleaved`（只允许 ≤1）；手动 SETUP/PLAY `interleaved=2-3` 后 1.2 s 无媒体。

**影响**：客户端看到 SETUP/PLAY 成功但没有画面，属于静默互操作失败。

**建议**：

1. 二选一并保持一致：允许 0-255（推荐，channel 是 8 位）；或 SETUP 对 >1 返回 461；
2. `WriteInterleavedRaw` 同步修改；
3. E2E 增加 `interleaved=2-3` 用例，断言有媒体且 `$` 帧 channel 正确。

**验收**：`interleaved=0-1` 与 `2-3` 都能收到媒体；非法 channel（如 255-0）返回 461。

### P0-4 RTCP SR/RR 未接线（部分闭环）

**现象**：`BuildSenderReport` 只在 `tests/test_rtcp.cpp` 使用；`RtspSession` 没有发送 SR 的周期逻辑；`OnInterleaved` 只刷新活动时间，不解析 RR/BYE。

**证据**：`BuildSenderReport` 只在 `src/rtcp.cpp`/单测定义，`RtspSession`/`RtspServer` 无调用；E2E 输出 `RTCP: not observed`。

**影响**：设计 §7.5 未实现；播放器收不到 SR，RR 丢包/抖动统计不生效，BYE 不处理。

**建议**：

1. 每 5 s（单播，随机化 0.5-1.5）发送 compound SR+SDES(CNAME)；
2. `OnInterleaved` 解析 RR/BYE，校验长度和 report count；
3. 统计 `rtcp_sr/rr/bad_packets`；UDP 走 `server_port+1`，TCP 走 RTCP channel；
4. 墙钟偏移只在启动采样，跳变不影响 RTP 时基。

**验收**：抓包可见 SR+SDES；客户端 RR 能被解析并计数；TEARDOWN/超时释放 session。

### P0-5 `input_seq` 未用于丢帧恢复（已闭环）

**现象**：`FrameIngress::Acquire()` 为每次尝试递增 `input_seq_`，并写入 `FrameDesc`；但 loop 和 session 从未读取它。源丢帧、oversize、`Acquire/Commit` 失败不会触发客户端 `AwaitIDR`。

**证据**：`frame_ingress.cpp` 的 `FrameIngress::Acquire`/`Commit`；全仓库无其他 `input_seq` 读取。

**影响**：丢失参考帧后客户端继续收 P 帧，表现为花屏/绿屏/解码错误；README 的“input_seq 缺口触发 IDR”当前不成立。

**建议**：

1. loop 维护 `last_input_seq_`；`DrainIngress` 发现 `desc.input_seq != last+1` 时，对所有 PLAY 会话调用 `OnInputGap()`；
2. `OnInputGap()` 释放队列和当前帧，进入 `AwaitIDR`；
3. 源侧 `ReadNextAu` oversize 丢帧、`SubmitAu` Acquire/Commit 失败也要产生可见 gap（例如递增 atomic `gap_seq_`）；
4. 加测试：中间丢一帧、oversize、队列满，断言客户端等待 IDR。

**验收**：注入丢帧后，客户端在下一个 IDR 恢复；统计 `idr_waits/idr_recoveries` 增长；无花屏回归。

### P0-6 测试基础设施与证据口径

**现象**：此前重复 E2E 曾失败，原因是 `make_real_stream.sh` 的 Bash 解析和 `build/rtspserver_demo` foreign process 误报；旧 `build/` 与新 `build_review/` 混用。本次快照 11/11 通过，但隔离机制仍需修。

**证据**：此前 `ctest -R test_e2e --repeat until-fail:3` 第一次 70.31 s 通过，第二次 70.36 s 失败；错误包含 `make_real_stream.sh: 行 66: 未预期的记号 "("` 与 `foreign rtspserver_demo processes=2`。本次快照 `test_e2e` 11/11 通过。

**影响**：单次通过不能作为稳定证据；测试报告容易被环境问题污染。

**建议**：

1. `RunProcess` 显式 `/bin/bash` 执行 `make_real_stream.sh`，或脚本改 POSIX sh；
2. 进程隔离只认本用例子进程 PID；不要因为其他构建目录的 server 进程判失败；
3. CI/本地固定一个 build 目录；测试前清理残留 `rtspserver_demo`；
4. 用例结束必须 `waitpid`/`kill` 子进程；本次评审发现 `19343/19344/19345` 端口的 `build/rtspserver_demo` 子进程在 `test_e2e` 返回后仍存活；
5. 测试报告记录 build 路径、二进制 hash、重复运行次数和失败原因。

**验收**：`ctest -R test_e2e --repeat until-fail:5` 连续 5 次通过；无 foreign process 误报；脚本在 `sh`/`bash` 下行为明确。

## 4. P1 问题

### P1-1 FU-A 每片复制（已闭环）

`h264_packetizer.cpp` 的 `H264Packetizer::Next` 将每个分片 `memcpy` 到 `cursor.fu_payload`。大 IDR 的每个分片、每个客户端都复制一次，违背“共享 AU payload”的设计。

**建议**：把 `RtpPacket` 扩展为“FU 头（2 字节）+ 共享分片视图”两段；`UdpRtpTransport`/TCP 发送用 3 个 iovec（interleaved/RTP header、FU 头、共享 payload）。这样 H.264/H.265 的 FU 路径不再复制 payload。

### P1-2 TCP 每包整段复制

`rtp_transport.cpp` 的 `WriteInterleaved` 把 header+payload 复制进 32 KiB `tx_`。16 客户端时，每个 AU 被复制 16 次，CPU 和内存带宽随客户端数线性增长。

**建议**：TCP 也使用 `sendmsg` + iovec + 游标；`tx_` 只保留控制响应和必要的少量头。短写时保留 iovec 游标，不把 payload 搬进 `tx_`。若为简化保留复制，必须在设计中明确“TCP 路径不是零拷贝”，并用 16 路实测 CPU 证明可接受。

### P1-3 重复 SETUP 非事务（已闭环）

`rtsp_session.cpp` 的 `RtspSession::HandleSetup` 先 `udp_.Close()` 再打开新端口；新端口失败时旧传输已丢失。设计 §3.6.2 要求“先创建新资源，复核后提交；失败回滚旧传输”。

**建议**：使用可移动的 `UdpRtpTransport` 或临时对象 `new_udp`；成功打开后复核 `transport_gen`，再交换；失败保留旧对象并返回 503。

### P1-4 8 个帧槽与 500 ms 阈值不匹配

`config.hpp` 的 `kFrameSlots` 是 8 槽；25 fps 下 320 ms 就周转一圈，设计中的 500 ms 年龄阈值永远到不了。慢客户端场景会先触发 F-01 池逐出，而不是 F-02 年龄丢弃。

**建议**：二选一并同步文档/测试：

- 内存优先：保留 8 槽，把最旧 AU 阈值改为 300 ms，重算 §5.2/§5.3；
- 设计优先：改 16 槽（4 MiB），总用户态约 4.7-5.2 MiB，仍在 6 MiB 预算内。

### P1-5 每连接 TX 32 KiB 与设计 8 KiB 不一致

`config.hpp` 的 `kRtspTxBytes` 为 32 KiB；16 连接多 384 KiB。控制 backlog 仍按 `kControlTxLimit=8192` 判定。

**建议**：若保留 32 KiB，更新设计预算和“控制响应积压”口径；若不需要承载整段 TCP 媒体（见 P1-2），可降回 8-16 KiB。

### P1-6 H.265 范围与 README 矛盾（已闭环）

README 第 7 行写“H.265 未实现”，但 `h265_packetizer.*`、`test_h265_packetizer`、E2E H.265 用例都已存在。

**建议**：明确 H.265 是 Phase 2：要么默认构建关闭（`RS_ENABLE_H265`），要么更新 README/设计并补真实 x265 流 + 播放器解码；不能保持“代码已实现、文档说未实现”的状态。

### P1-7 SPS 校验缺失

`sdp.cpp:141-177` 只检查参数集非空和长度；`profile-level-id` 直接取 `sps[1..3]`，没有校验 profile_idc/chroma/bit_depth/frame_mbs_only。

**建议**：在 `LoadParamSets` 或 `BuildSdp` 前校验；不支持的高 10/4:2:2/4:4:4/场编码返回 415；`sprop-parameter-sets` 使用去除起始码的 NAL，并处理 trailing zero。

### P1-8 `std::thread` 创建失败会终止进程（已闭环）

`rtsp_server.cpp` 的 `RtspServer::Start` 使用 `std::thread`；在 `-fno-exceptions` 下创建失败通常直接 terminate，无法返回 `ServerError`。

**建议**：改用 `pthread_create` 并显式处理 `EAGAIN`；或在设计/构建中明确接受“线程创建失败即终止”，但启动失败清理路径要一致。

### P1-9 `std::atomic<uint64_t>` 在 ARMv7 可能不是 lock-free（已闭环）

`rtsp_server.hpp` 的 `source_dropped_`/`source_committed_`/`source_oversize_` 使用 64 位原子计数。ARMv7 上可能依赖 libatomic/锁，且 `-fno-exceptions` 构建需要确认链接。

**建议**：加 `static_assert(std::atomic<uint64_t>::is_always_lock_free)`（若目标不满足则改 32 位计数或普通 loop-only `uint64_t` + 快照）；ARM 交叉构建验证。

### P1-10 数据竞争与计数归属（已闭环）

`FrameIngress::orphan_drops_` 同时由 producer（`Abort`）和 loop（`ReturnSlot`）递增，非原子；属于数据竞争。`slot_len_/gen_/refs_` 的跨线程可见性依赖 SPSC 队列同步，缺少 TSan 证据。

**建议**：把 producer/loop 的 orphan 计数分开（或 `std::atomic`）；用 TSan 跑 `test_frame_ingress` 的并发用例；在注释中明确每个数组的线程归属和同步边。

## 5. P2 与结构性建议

### P2-1 用 `CodecOps` 静态表收敛 H.264/H.265 分支

`RtspSession` 里多次 `codec_ == kH265` 分支（`ResetCursorState`、`StartCursor`、`NextPacket`、`CursorSeq/Ts`、SDP）。建议定义：

```cpp
struct CodecOps {
  void (*reset)(ClientCursor&) noexcept;
  void (*start)(ClientCursor&, uint32_t, uint32_t, bool) noexcept;
  osp::expected<RtpPacket, PacketizeError> (*next)(const uint8_t*, uint32_t, const ParamSets&, ClientCursor&, uint32_t) noexcept;
  uint16_t (*seq)(const ClientCursor&) noexcept;
  uint32_t (*ts)(const ClientCursor&) noexcept;
};
```

用 `constexpr` 表按 codec 选择。注意函数指针可能抑制内联；先用 `.text` 和 P99 测量，再决定是否保留模板/`if constexpr` 版本。

### P2-2 `std::from_chars` 替换手写数字解析

`rtsp_parser.cpp`/`rtsp_session.cpp` 的 `ParseU32`/`ParseDecimal` 可用 `std::from_chars`（无 locale、无异常），但先测代码尺寸和 ARM 性能；若收益不明显，保留手写循环。

### P2-3 请求/状态分派表

`HandleRequest` 的 `switch` 和 `HandleUnsupported` 可以收敛为 const 表 `{method, allowed_states, handler}`；与 P2-1 一样，先测可读性和代码尺寸，不强行模板化。

### P2-4 安全边界补强

- `ClassifyUri` 只按路径匹配，未校验绝对 URI 的 host/port；建议拒绝非本机 host。
- session ID 由 `SplitMix64(id_seed)` 扩展，不是 CSPRNG；无鉴权场景风险有限，但若后续加鉴权，需改用 `getrandom` 直接生成。
- 无鉴权/无 TLS 的部署边界要写入 README 和启动日志；Shell 默认关闭。

### P2-5 测试矩阵补齐

- 16 路 × 4 Mbps × 600 s；16 路同时 IDR；最慢客户端持有 4 AU。
- 真实 H.264（x264）与 H.265（x265）各 30 min；VLC/ffplay/目标播放器。
- ASan/UBSan、TSan 分开构建；`test_frame_ingress`/`test_rtsp_server` 并发用例。
- ARM 交叉编译 + 板测：32 位 `uintptr_t` tag、64 位原子、对齐、CPU/温升。

### P2-6 文档对齐

8/16 槽、32 KiB TX 的描述仍不一致；H.265 的 README 已更新。建议增加一张“设计值 / 实现值 / 验证状态 / 裁决”表，避免后续实现和验收各取一套。

### P2-7 调试命令面

P0/P1/P2 命令面均已落地：`docs/2026-11-26-调试命令面设计.md` + `include/rs/debug_shell.hpp` + `src/debug_shell.cpp`。只读 13 条；受控 `log/kick/reset/trace/shutdown` 与 P2 `fault drop/stall/eagain/idr`、`simulate slow` 经 `ShellCommand` SPSC + `Wake()` 回到 loop 执行；`idr` 对文件源返回 not supported。P2 需 `RS_ENABLE_FAULT_INJECTION=ON`，`DebugShell` 默认关闭。命令注册集中在 `RegisterShellCommands()`，不再使用 `g_server` 和多个 `ShellAutoReg` 全局对象。

### P2-8 文件源与 RtspServer 耦合

已完成：文件读取、Annex B AU 切分、SPS/PPS 扫描和 source 线程移入 `rs::FileSource`；`RtspServer` 不再依赖文件路径，改为接收 `ServerConfig.params`，并公开 `Ingress()`/`Callbacks()` producer 边界。`test_server_external` 验证无文件启动、`Ingress()` 提交和停止。`src/rtsp_server.cpp` 从约 1320 行降到约 997 行；`FileSource` 约 437 行。后续把源缓冲改为 offset 读、去掉每 AU `memmove`；16 路复跑无回归。

### P2-9 RtspSession 拆分

已完成：媒体队列/游标/令牌桶移入 `MediaSender`；控制响应与 TCP 媒体缓冲移入 `TxStream`；RTCP 周期/解析移入 `RtcpEndpoint`。`RtspSession` 保留控制面 facade，约 1217 行；`MediaSender` 约 243 行，`TxStream`/`RtcpEndpoint` 为头文件小类。

### P2-10 UDP RTCP watcher

已完成：`UdpRtpTransport` 暴露 `RtcpFd()`/`RecvRtcp()`；`RtspServer` 用固定 `UdpWatch` 表和 slot tag 注册 RTCP fd，TEARDOWN/关闭时移除；`watchers_used` 计入 UDP watcher。手动 UDP 客户端发送 RR 后，`client 0` 显示 `rtcp rr=1`。

### P2-11 16 路压力测试与 TCP `tx_` 评估

已完成 60 s、16 路（8 TCP + 8 UDP、4 Mbps/路）x86 冒烟：16/16 客户端存活，RSS 5600 KB 恒定，FD 40，线程 3，优化前 CPU 平均 20.42%/最大 24.34%、loop P99 187 us；FileSource 去掉每 AU `memmove` 后复跑 CPU 平均 21.26%/最大 27.45%、loop P99 173 us，属同量级噪声且无回归。无 AU Drop/gap。结论：当前 x86 数据不足以证明 `tx_` 复制是瓶颈，暂不实施 iovec/零拷贝；等目标平台 `perf` 证据后再定。详见 `docs/2026-11-26-16路压力测试与TCP-tx评估.md`。

### P2-12 网络 socket 配置

已落地：listener backlog 32；accepted TCP `SO_SNDBUF=64 KiB`、`SO_RCVBUF=32 KiB`、`TCP_NODELAY`、`TCP_NOTSENT_LOWAT=16 KiB`、`TCP_USER_TIMEOUT=10 s`、`SO_KEEPALIVE`、`CLOEXEC`；UDP RTP/RTCP `SO_SNDBUF=128 KiB`、`SO_RCVBUF=32 KiB`、connected socket、`IP_TOS=EF`、CLOEXEC。newosp 增加 `accept4` 与 `EPOLLRDHUP` 映射；impl 使用 `Accept4(SOCK_NONBLOCK|SOCK_CLOEXEC)`。新增固定表 per-IP accept/request 令牌桶（32 项；accept 32 burst/8 每秒，request 256 burst/128 每秒）。`net` 命令暴露 `TCP_INFO` 的 RTT/cwnd/retrans/unacked/notsent 和实际 sndbuf/rcvbuf。

仍非“绝对最优”：PMTU 未做主动探测；DSCP 依赖网络策略；目标平台（ARM Linux 或 RS500 RISC-V RT-Thread）未实测，参数不是板级最优值。

## 6. PHZ76/RtspServer 借鉴清单

### 6.1 值得挖掘

| PHZ76 资产 | 用法 |
|---|---|
| `src/xop/H264Source.cpp`、`H265Source.cpp` | NAL 切分、FU-A/FU 分片的测试 oracle；逐字节对比当前 packetizer |
| `src/xop/RtspConnection.cpp` | OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN 流程、Transport 解析、状态码、interleaved 帧 |
| `src/xop/MediaSession.cpp` | SDP、track control URI、RTP-Info、每客户端 RTP 状态 |
| `src/xop/RtpPacket.cpp`、`RtpSink.cpp` | seq/timestamp/marker/FU-A 规则 |
| `src/xop/RtspServer.cpp` | 连接/session 生命周期与异常路径 |
| CSDN 文章与 H.265 问题 | 回归输入，不作为“修复已证实”的证据 |

### 6.2 不应照搬

- `MediaSession` 对每个连接复制 RTP 包。
- `RtspConnection` 超长缓冲 `RetrieveAll()` 清空。
- `EpollTaskScheduler` 静默 `epoll_ctl` 失败。
- 每连接线程 / `shared_ptr` 所有权网络。
- 动态增长缓冲、全局常量替换（`RTP_TCP_HEAD_SIZE=0`、1420→1440）。
- H.265 的起始码/NAL 处理不能直接复用 H.264 FU-A 规则。

### 6.3 落地方案

新增 `docs/phz76-conformance.md` + 一组一致性测试：

1. 用同一组 RTSP 请求（OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN、异常路径）分别打 PHZ76 和当前 server；
2. 对比状态码、关键头、SDP 字段、`RTP-Info`、`Transport` 回显；
3. 抓包对比 RTP seq/marker/timestamp/FU-A 头；
4. 记录“有意差异”（如不复制 payload、不共享 sink 状态），而不是追求字节完全一致。

## 7. C++17 高性能特性使用建议

### 7.1 应使用

| 特性 | 用法 |
|---|---|
| `constexpr` + `static_assert` | 容量、对齐、tag 宽度、帧槽/队列关系 |
| `osp::expected` + `[[nodiscard]]` | 所有可能失败的接口 |
| `osp::span` / `std::byte` | 零拷贝视图和缓冲区 |
| `std::array` | 固定表、直方图、连接槽 |
| `enum class` | 状态、错误、codec、transport |
| `alignas(64)` | 帧槽、跨线程共享元数据 |
| `std::atomic` 显式内存序 | 跨线程停止/唤醒/计数；ARMv7 先确认 lock-free |
| `if constexpr` / `constexpr` 表 | codec/transport 分支收敛（先测代码尺寸） |
| `std::from_chars` | 冷路径数字解析（可选） |
| `std::optional` | 冷路径（配置/测试） |

### 7.2 不应使用

- `std::shared_ptr`、`std::function`、`std::regex`、`std::iostream`。
- `std::string`/`std::vector`/`std::map` 热路径。
- `std::async`、每客户端线程、`std::variant` 作为每包视图。
- 协程/`std::execution`（C++20 或依赖 TBB/异常）。
- 为了“用上 C++17”引入的模板层、类型擦除或额外间接。

### 7.3 当前代码评价

当前 `src/` 已经用对了主要特性：无堆容器、`osp::expected`、`osp::span`、`static_assert`、`alignas`、`std::atomic`、`enum class`、`[[nodiscard]]`。**不要为了“充分挖掘 C++17”而重写这些部分。**

### 7.4 真正的性能优先级

1. 去掉 FU-A/TCP payload 复制（P1-1/P1-2）。
2. 修正全局桶与 `Admit` 双扣（P0-1）。
3. 发送调度改为时间预算（如 2 ms）+ 立即续跑，而不是固定 16 包后等下一帧。
4. 测量 16 路 CPU、P99 loop 延迟、每客户端吞吐，再决定是否需要 `CodecOps`/批量 `sendmmsg`。
