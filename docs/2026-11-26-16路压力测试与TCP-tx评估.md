# 16 路压力测试与 TCP `tx_` 评估

> 日期: 2026-11-26
> 构建: `build_review`（`RS_ENABLE_DEBUG_SHELL=ON`、`RS_ENABLE_FAULT_INJECTION=ON`）
> 场景: x86_64 host，8 TCP interleaved + 8 UDP，H.264 4 Mbps/路，60 s，`ffmpeg -c copy`
> 结论: 16 路通过；当前 x86 数据不足以证明 `tx_` 整段复制是瓶颈，暂不实施 iovec/零拷贝改造

## 1. 执行命令

```bash
cd /home/dgliu/workspace/osp-rtspserver
BUILD="$PWD/build_review" DURATION=60 INTERVAL=5 \
  CLIENTS_PER_TRANSPORT=8 KBPS=4000 ./scripts/stress.sh
```

生成流：`make_real_stream.sh`，H.264，4 Mbps 目标码率，60 s + 5 s 余量。

- 这是 60 s 冒烟，不是 600 s 长稳；不是 ARM 板测；`-c copy` 不包含解码负载。

## 3. TCP `tx_` 复制评估

当前 `TxStream` 仍是“控制响应 + TCP interleaved 媒体共用一块 32 KiB 线性缓冲”，`WriteInterleaved` 把 header + prefix + payload 复制进 `tx_`。理论上这是每客户端每包一次复制。

本次 x86 结果：

- 16 路（8 TCP + 8 UDP）总出口约 64 Mbps，服务端 CPU 平均 20.42%、最大 24.34%；
- loop P99 187 us，无主动丢 AU、无 gap、无 send stall；
- 没有出现“TCP 复制把 loop 拖爆”的证据。

结论：**暂不实施 iovec/零拷贝改造**。原因：

1. 当前瓶颈没有通过测量定位到 `memcpy`/`WriteInterleaved`；
2. `tx_` 的线性缓冲同时保证了 interleaved 帧的原子性和控制响应顺序，改成 iovec 游标会扩大状态机和短写复杂度；
3. 目标平台是 ARM，x86 的 20% CPU 不能直接换算。

## 4. 何时重新评估

满足任一条件再启动 iovec/零拷贝：

1. ARM 板测 16 路 × 4 Mbps 时，服务端 CPU 超过产品预算的 60%；
2. `perf record` 显示 `memcpy`/`WriteInterleaved`/`TxStream` 相关路径占服务端 CPU >20%；
3. 只跑 TCP（16 路）时 loop P99 明显高于 UDP 同负载，且可归因到 `tx_` 复制；
4. 产品要求 8 Mbps/路或更大并发，线性缓冲的复制带宽成为可测瓶颈。

改造时的目标形态：

- `TxStream` 只保存控制响应和必要的少量头；
- RTP 头 + 可选 FU 前缀 + 共享 payload 通过 `sendmsg` iovec 发送；
- 保留“一个 interleaved 帧不可插入响应”的串行游标；
- 短写状态从单块 `tx_` 游标改为 iovec 游标，必须保持 2 s 卡死关闭语义。

## 5. 限制

- 仅 60 s，未覆盖 600 s 长稳、内存碎片、fd 复用风暴；
- 仅 x86_64，不代表 ARM/RISC-V CPU/DDR/网口；
- 本机没有 `arm-linux-*` 交叉工具链，也没有 `perf`/`valgrind`，因此本轮无法执行目标平台采样；
- `RS500_RTSP` BSP 实际是 RISC-V RT-Thread（`riscv64-unknown-elf`），当前 `impl` 依赖 Linux `pthread`/epoll/`getrandom`，不能直接在该 BSP 运行；若产品目标是 RS500，需要先做 RT-Thread/LwIP 适配；
- `ffmpeg -c copy` 不验证解码正确性，只验证传输和资源；
- UDP 客户端 `video_kib` 是客户端计数，不是服务端出口计数。

## 6. 网络 socket 配置复核

已落地并通过 `strace -e setsockopt,accept` 验证：

- listener：backlog 32、`SO_REUSEADDR`、nonblocking、`CLOEXEC`；
- accepted TCP：`SO_SNDBUF=64 KiB`、`SO_RCVBUF=32 KiB`、`TCP_NODELAY`、`TCP_NOTSENT_LOWAT=16 KiB`、`TCP_USER_TIMEOUT=10 s`、`CLOEXEC`；
- UDP RTP/RTCP：connected、nonblocking、`SO_SNDBUF=128 KiB`、`SO_RCVBUF=32 KiB`、`CLOEXEC`、端口对偶数 RTP + `RTP+1` RTCP。

进一步补齐：newosp `accept4(SOCK_NONBLOCK|SOCK_CLOEXEC)`、`EPOLLRDHUP` 映射；`SO_KEEPALIVE(30/10/3)`；UDP `IP_TOS=EF`；固定表 per-IP accept/request 令牌桶；`net` 命令读取 `TCP_INFO` 和实际 sndbuf/rcvbuf。

配置后同一 16 路 60 s 场景复跑：16/16 存活，loop P50/P95/P99 = 6/125/197 us，无 AU Drop/gap/qdrop；CPU 平均 25.25%、最大 29.24%。多轮 CPU 在 18.9%-25.3% 波动，属宿主负载噪声，无功能回归。

仍不是“绝对最优”：

- PMTU 未做主动探测；DSCP 是否生效取决于网络策略；
- 没有更细的 per-IP 请求分级（当前 accept/request 是固定令牌桶）；
- 目标平台（ARM Linux 或 RS500 RISC-V RT-Thread）未实测，不能宣称参数最优。
