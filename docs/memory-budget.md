# 并发槽位与帧池的内存方案分析

> 适用版本：`rs_rtsp` 0.1.x（newosp 基线 `5ef966c`）。
> 测量平台：x86_64，GCC 11，`-fno-exceptions -fno-rtti`，`RelWithDebInfo`。
> 本文只回答一个问题：长期并发不超过 4 路时，如何把为 16 路预留的内存收回来，且不破坏"零堆 + 可预测"的既有契约。

## 摘要

- 每连接槽实际成本约 **42.8 KiB**（`RtspParser` 8 KiB + `RtspSession` 33.4 KiB + socket 与统计），16 槽约 **702 KiB**。
- 更大的固定成本是帧池 **8 × 256 KiB = 2 MiB**，与客户端数量无关。
- 三个方案按"收益 / 风险"排序：A 编译期槽位（省 514 KiB，低风险）、B 帧池槽位（省 1 MiB，中风险）、C 发送区池化（省约 400 KiB，中高风险，仅在"多连接少播放"时才有意义）。
- 建议先做 A；B 需要补一轮抖动回归；C 只在产品明确存在 16 连接但 ≤4 路播放时启动。
- 动态分配槽位（D）违反零堆契约，不进入候选。

## 1. 现状测量

| 配置 | `sizeof(RtspServer)` | 备注 |
|---|---:|---|
| `RS_MAX_CONNECTIONS=16` | 2,817,728 B（2.69 MiB） | 当前默认 |
| `RS_MAX_CONNECTIONS=8` | 2,466,752 B（2.35 MiB） | |
| `RS_MAX_CONNECTIONS=4` | 2,291,264 B（2.19 MiB） | |

由三档差值可得每槽增量 **43,872 B（42.8 KiB）**。

### 1.1 槽位构成

| 成员 | 大小 | 说明 |
|---|---:|---|
| `RtspParser` | 8 KiB | 每连接独立的半包接收缓冲，不能跨连接共享 |
| `RtspSession::tx_`（`TxStream`） | 32 KiB | 控制响应与 TCP 交织媒体的共用发送区 |
| `RtspSession` 其余 | 约 1.4 KiB | 媒体游标、令牌桶、RTCP 端点 |
| socket、代际、统计字段 | 约 1.4 KiB | 连接表元数据 |

### 1.2 固定底座

4 槽构建仍有 2.19 MiB，其中帧池 2 MiB（`kFrameSlots=8`、`kMaxAuBytes=256 KiB`），其余约 120 KiB 是帧入口队列、参数集、poller 与告警缓冲。**要显著降内存，必须同时动帧池**。

## 2. 四个杠杆

| 杠杆 | 现状 | 单次节省 | 主要代价 |
|---|---|---:|---|
| L1 连接槽数 | 16 | 16→4：514 KiB | 按产品重编译；第 5 个连接被拒 |
| L2 帧池槽数 | 8 | 8→4：1 MiB | 在途 AU 深度减半，突发 IDR 时更早触发丢帧与 IDR 请求 |
| L3 出站发送区 | 每槽 32 KiB 常驻 | UDP-only：约 28 KiB/槽；池化：约 400 KiB（16 连接 / 4 播放） | 改动发送路径与失败语义 |
| L4 动态槽位 | 未使用 | 理论最优 | 破坏零堆契约，引入分配失败分支，不采用 |

## 3. 方案 A：编译期连接槽数

**做法**：`kMaxConnections` 由 CMake 变量 `RS_MAX_CONNECTIONS` 注入，默认 16，范围 1..256，越界在配置阶段报错；`ServerConfig::max_clients` 默认值随之收敛。

**收益**：4 路产品从 2.69 MiB 降到 2.19 MiB（省 514 KiB），且不引入任何运行期判断。

**代价与风险**：
- 每增加一个产品档位就多一次构建与回归；需要把档位写进发布说明。
- 第 N+1 个连接在 accept 阶段被拒，行为与今天的 `max_clients` 上限一致，测试需覆盖。
- 槽位数与 tag 编码、poller 事件预算联动（`kMaxConnections ≤ 256`、`kMaxPollEvents = 64` 已有限制），改动后需跑一遍 fd 上限用例。

**改动面**：`include/rs/config.hpp`（一个常量 + 注释）、`CMakeLists.txt`（一个缓存变量 + 校验 + 编译定义），约 20 行。

**验证**：x86 双配置（16/4）全量 `ctest`；aarch64 与 armhf 交叉编译 + qemu 执行；新增"第 N+1 个客户端被拒绝"用例。

## 4. 方案 B：帧池槽数可配

**做法**：把 `kFrameSlots`（当前 8）与 `kEmptySlotQueueDepth`、`kInputQueueDepth` 一起暴露为 CMake 变量，保持"2 的幂、空槽队列不小于帧槽数、输入队列不大于帧槽数"三条静态断言。

**收益**：8→4 直接省 1 MiB，是单笔最大的收益。

**代价与风险**：
- 8 槽在 40 ms 节拍下提供约 320 ms 的在途 AU 深度，4 槽只有约 160 ms；编码器突发 IDR（I 帧通常是 P 帧的 3~5 倍）时更早触发 `Acquire` 失败，进而让所有播放会话进入 AwaitIDR。
- 需要重新标定"输入缺口 → IDR 请求"的限频参数，避免弱网或突发时 IDR 风暴。
- 必须重跑 16 路 4 Mbit/s 60 s 的抖动回归，确认 gap、队列丢弃、发送停滞仍为 0。

**验证**：16 路 60 s、120 s 两轮；IDR 密集流（1 s GOP）一轮；慢客户端黑洞场景一轮。

## 5. 方案 C：出站发送区池化

**做法**：把每槽 32 KiB 的 `TxStream` 拆成两部分——
- 每槽常驻 4 KiB 控制区，只放 RTSP 响应与 RTCP；
- 32 KiB 媒体区放进共享池，仅在 TCP 传输且进入 PLAY 时获取，TEARDOWN 或关闭时归还。

**收益**：16 个 RTSP 连接、4 路 TCP 播放时，槽位内存从约 702 KiB 降到约 300 KiB（省约 400 KiB）；UDP 播放不占用媒体区。

**代价与风险**：
- 发送路径从"每槽一个流"变成"控制流 + 可选媒体流"，`Pending()`/`Consume()`/水位判断都要分叉，是三个方案里唯一触碰媒体热路径的。
- 需要定义"媒体区耗尽"的语义：拒绝 PLAY（453/503）、回落到 UDP，还是允许排队等待。任一选择都会改变客户端可见行为。
- 回归范围最大：TCP/UDP 混跑、慢客户端、断线重连、交织帧边界。

**适用前提**：产品确实存在"16 个 RTSP 连接、长期 ≤4 路播放"的部署。若长期并发就是 ≤4，方案 A 更省（171 KiB）也更简单。

## 6. 对比矩阵

| 目标形态 | A 槽位 | B 帧池 | C 池化 | A+B | A+B+C |
|---|---:|---:|---:|---:|---:|
| 4 路、TCP+UDP 混合 | 2.19 MiB | 1.69 MiB | 2.19 MiB | 1.19 MiB | 1.19 MiB |
| 16 连接、4 路 TCP 播放 | — | — | 2.30 MiB（估算） | — | 约 1.4 MiB（估算） |
| 16 路全开 | 2.69 MiB | 1.69 MiB | 2.69 MiB | 1.69 MiB | 约 2.4 MiB |

注：C 的行为估算基于"每槽常驻 4 KiB 控制区 + 4 个 32 KiB 媒体区"，未含对齐与元数据开销，落地时以实测为准。

## 7. 推荐路径

1. **先做 A**：改动最小、收益确定、无运行期风险，一个提交可完成，并同步更新架构文档的容量表与博客的取舍表。
2. **评估 B**：需要产品先确认"可接受的 IDR 触发频率"与"最小 AU 深度"；确认后再跑一轮抖动回归，数据达标才合入。
3. **C 暂缓**：等出现"多连接、少播放"的真实部署需求再启动，避免为了 400 KiB 改动媒体热路径。

## 8. 决策所需的输入

| 问题 | 影响 |
|---|---|
| 长期并发上限是 4 还是可能到 8/16 | 决定 A 的槽位档位 |
| 传输方式以 UDP 还是 TCP 为主 | 决定 C 是否有价值 |
| 典型 AU 大小、码率、IDR 间隔 | 决定 B 的帧池深度 |
| 产品能否接受"每档位一次编译与回归" | 决定 A 是否足够 |
| 是否允许第 5 个连接被拒 | 决定是否需要运行期弹性（即 C 或 D） |

## 9. 附录：测量方法

```sh
# 槽位占用：直接对头文件取 sizeof，避免受构建目录影响
for n in 4 8 16; do
  g++ -std=c++17 -fno-exceptions -fno-rtti -DRS_MAX_CONNECTIONS=$n \
      -I include -I ../newosp/include -x c++ - -o /tmp/sz$n <<'SRC'
#include "rs/rtsp_server.hpp"
#include <cstdio>
int main() { std::printf("%zu\n", sizeof(rs::RtspServer)); return 0; }
SRC
  echo -n "slots=$n size="; /tmp/sz$n
done
```

单槽增量 = (16 槽占用 − 4 槽占用) / 12 = 43,872 B。
